# Ревью архитектуры и кода

Дата: 21.10.2026. Область: проверка договоров, диалог, учебное сравнение и сдача
по [плану урока](https://university.zerocoder.ru/pl/teach/control/lesson/view?id=345148516&editMode=0).

## Найденные и исправленные проблемы

| Приоритет | До ревью | Исправление |
| --- | --- | --- |
| Высокий | Проверка реального договора импортировала настройки и валидатор из самостоятельного учебного CLI; HTTP-запросы и чтение ключа дублировались | Общий `contract_core.py`, один API-клиент, одна конфигурация, независимые сценарии |
| Высокий | Диалог использовал `answer/references/notes`, хотя задание требует `title/steps/notes` | Одна строгая JSON Schema для всех режимов; весь текст промптов — в `prompts.json` |
| Высокий | Ограничение истории числом сообщений не ограничивало суммарный объем длинного договора и вопросов | Закрепленные договор и первая проверка; до 10 полных успешных пар; дополнительный предел символов |
| Средний | Успешным мог считаться JSON с нештатной причиной завершения, кроме `length` | Принимается только `finish_reason=stop`; отказ и неполный ответ не включаются в историю |
| Средний | Word-текст внутри вложенных абзацев и `AlternateContent` мог извлекаться дважды | Извлечение одного варианта и исключение повторного текста вложенных абзацев; удаленные правки пропускаются |
| Средний | Реальному договору навязывалось минимум 5 замечаний с заполнением недостающих пунктов | Допускается 1–8 приоритетных действий; выдумывать риски запрещено |
| Средний | Проверка учебных промптов требовала одновременно менять роль и few-shot | Разрешено менять роль **или** мини-пример; в текущем задании изменена только роль |
| Средний | Старые результаты переносились до успеха нового запроса, таблица README устаревала после повторений | Отдельная папка каждого запуска; указатель меняется после успешной пары; метрики рассчитываются из сохраненных ответов |
| Средний | Telegram-бот, зависимость `aiogram`, старые логи, эксперименты и документация не относились к проверке договора | Удалены из проекта; рабочие зависимости — только `requests` и `python-dotenv` |

## Итоговая архитектура

Один небольшой консольный проект из пяти модулей: `main.py`, `contract_core.py`,
`documents.py`, `dialogue.py`, `experiment.py`. Нет сервера, Telegram, базы данных
и вспомогательных CLI-оберток. Команды VS Code запускают только `main.py`.

Учебное задание сохранено целиком: мини-задача, четыре части промпта, первый
запуск, одна итерация роли при одинаковых параметрах, сравнение и пользовательский
артефакт. Проверка настоящего договора и диалог остаются рабочими возможностями.

## Данные и воспроизводимость

- Исходные ответы модели сохраняются; JSON не восстанавливается из Markdown.
- Файлы результатов записываются через временный файл и замену, без частично записанного JSON.
- Неудачный запрос не изменяет успешную историю и не повторяется автоматически.
- ZIP собирается по списку разрешенных файлов и включает только последний успешный учебный эксперимент.
- Личные проверки и `.env` сохранены локально и не включаются в архив; перед упаковкой проверяются значения секретов из `.env`.
- До очистки создана резервная копия исходного кода и учебных материалов вне папки проекта; личные договоры и `.env` в нее не копировались.

Анализировались все пять рабочих модулей. Pyright запускался с доступом к
виртуальному окружению, поскольку из песочницы не определялись пути библиотек.
На момент ревью Git-репозитория в папке не было; состав файлов сверялся с резервной копией до очистки.
Зависимости Ruff, Pyright и Coverage установлены только как инструменты проверки
в окружение и не добавлены в рабочие `requirements.txt`.

Реальные ответы, параметры и содержательная оценка находятся в
[учебном сравнении](contract_results/README.md). Локальные тесты проверяют
поведение программы и формат данных, а не юридическую правильность выводов модели.
